## Components

| Component | Responsibility | Tech | Owner |
| --- | --- | --- | --- |
| **web** | Server-rendered frontend, marketing pages and the logged-in app | Next.js, TypeScript | Product team |
| **api** | The single REST API used by web, mobile and partners. Authentication, business logic, validation | Node.js, TypeScript | Product team |
| **worker** | Asynchronous jobs: emails, PDF generation, webhooks out, scheduled tasks | Node.js, same codebase as api | Product team |
| **Postgres** | System of record. One primary, one read replica for reporting | Managed Postgres 17 | Platform team |
| **Redis** | Cache, sessions, rate limiting. Losing it is an inconvenience, not data loss | Managed Redis | Platform team |
| **Job queue** | Durable queue between api and worker, with retries and a dead-letter queue | Postgres-backed queue ([ADR 0002](/architecture/adr/0002-postgres-backed-job-queue/)) | Platform team |
| **Object storage** | Uploaded files, generated PDFs, exports | S3-compatible | Platform team |

## Key flows

**A user request.** The browser hits the CDN, which serves static assets from cache and forwards
everything else to the load balancer. `web` renders pages and calls `api` server-side for data. `api`
authenticates the session, checks permissions, reads and writes Postgres, and returns JSON (see the
[API design guidelines](/practices/api-design/)).

**Slow work.** Anything that takes more than ~200 ms or talks to a flaky third party (emails, PDFs,
outgoing webhooks) is enqueued by `api` *in the same database transaction* as the change that caused
it, and executed by `worker`. Jobs are idempotent and retried with exponential backoff.

**Payments.** `api` creates payment intents with the provider synchronously. The final state arrives
asynchronously through signed webhooks, which `api` verifies, stores and acknowledges immediately,
handing processing to `worker`.

## Environments

| Environment | Purpose | Deploys | Data |
| --- | --- | --- | --- |
| Local | Development | — | Seed data in Docker |
| Preview | One per pull request, for reviewing UI changes | Every push to a PR | Seed data |
| Staging | Integration and end-to-end tests, demos | Every merge to `main` | Synthetic data, refreshed weekly |
| Production | Customers | After staging passes, via canary | Real data |

See the [deployment checklist](/operations/deployment-checklist/) for how a change moves through them.

## Design principles

- **Boring technology.** We choose well-understood tools and spend our innovation budget on the product.
- **One database until it hurts.** Postgres does more than people expect: queues, search, JSON. See [ADR 0001](/architecture/adr/0001-modular-monolith/).
- **Idempotency everywhere.** Retries are normal, so every job and every write endpoint must be safe to repeat.
- **Observable by default.** Every service emits structured logs with a request ID, RED metrics (rate, errors, duration) and traces.
